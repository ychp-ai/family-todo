# 数据库与云函数成本优化计划

日期：2026-09-16。状态：按用户授权顺序实施中；本地完成与云端验证分别记录，2026-09-17 已发布服务端、完成索引回填和一次过期会话清理，详见验收记录。

## 1. 目标与依据

目标是降低相同业务量下的总资源消耗，同时降低函数执行逻辑复杂度，保持既有业务、权限、历史与重试语义。

用户提供的近几天截图：

| 资源 | 用量 | 消耗 |
| --- | --- | --- |
| 文档数据库调用 | 约 23.53 万次 | 4705.6 点 |
| 文档数据库容量 | 展示为 0 MB·天，实时存储 0 MB | 不能据此认定实际无数据 |
| 云函数 | 7096 次，1831 GBs | 213.32 点 |

两项合计 4918.92 点，数据库约占 95.7%。若统计环境和时间范围一致，数据库调用与函数调用之比约为 33.16；这不是逐接口测量，可能包含控制台、迁移、测试和其他访问。若全部函数调用均使用仓库的 256 MB 配置，平均资源量约对应 1.03 秒/次；不是 CPU 时间，也不是客户端端到端延迟。

优先顺序：减少无效刷新与数据库往返 → 缩小扫描范围 → 减少分页重复计算 → 治理存储增长 → 根据实测调节运行时配置。

### 优化目标（验收目标，非收益承诺）

在同数据、同操作序列的固定基准下：

- 常见首页流程的应用层数据库调用总数下降至少 50%，争取 70%；记录平台实际计费口径差异。
- 无变化的连续前台刷新场景数据库调用下降至少 70%，仍维持当前刷新时效。
- 常见读接口 p95 与完整页面加载的累计 GBs 下降至少 30%，错误率和超时率不增加。
- 大结果完整翻页不再按“页数 × 所有缓存块”重复扫描；日常日期查询不读取可在数据库端排除的一次性事项。
- 查询会话清理稳定运行后，过期超过宽限期的数据不持续净增长；幂等回执和必要历史不丢失。

若某项基线已经很低，报告绝对节省量并按总成本决定是否继续，不为达到百分比增加架构复杂度。

## 2. 不变的业务与工程边界

- 保留原生小程序、单一 api 云函数、CloudBase 和现有分层，不引入新付费资源。
- 不调整 UI，不擅自延长 30 秒刷新时效、不截断提醒或历史范围，不用局部结果冒充完整统计。
- 保留可信身份、即时撤权检查、成员继任、历史执行人快照和本人关闭提醒优先规则。
- 保留持久化幂等、原 requestId 重试、事务版本检查和未知提交结果恢复；不能删除回执使旧请求再次执行。
- 历史个人数据未指定迁移账号和家庭，不执行业务归属迁移。技术字段回填不能改变归属。
- 不预生成所有未来次数，不将无限历史嵌入单个文档，不依赖跨请求权限缓存。
- 当前会话已授权按顺序实施本地代码和验证。生产清理、索引变更、部署、提交和推送仍以单独授权为准。

## 3. 已有能力，避免重复实施

已实现次数状态和提醒回执批量读取、事项候选每批 20 条、请求内部分上下文复用、事务读缓存、summary 响应、历史空窗跳跃、大结果次数块、前端同请求合并、30 秒页面缓存、小规模进度直接返回。过期会话清理脚本和 expiresAt 索引已存在，发布记录显示尚未执行云端清理。

当前剩余问题：批量多数局限于单事项；日期投影仍先扫描整个作用域的候选；个人扫描读到家庭事项后再丢弃；分页次数块仍反复重扫；summary 只精简响应，存储仍读完整文档；首页定时刷新仍分别查询家庭、事项和提醒。

## 4. 实施阶段

### A. 成本基线与可复现验收（P0，所有优化的前置）

1. 核对账单环境、时间范围、函数配置和计费明细；区分真实使用、开发者工具常驻轮询、验收脚本、迁移与控制台访问。
2. 复用 api.performance，补充聚合维度：集合/操作类别、身份与上下文、候选扫描、片段/控制/状态、排序聚合、会话持久化的耗时与调用数。指标不记录用户内容、OpenID、口令或完整 payload。
3. 增加客户端一次逻辑操作及完整分页链的关联观测，统计调用页数、空续页、游标失效重启与累计函数时间。服务端不能信任客户端关联字段作身份依据。
4. 区分数据库等待、CPU 投影和序列化；并行操作耗时不能简单相加当墙钟时间。默认关闭细粒度观测，可抽样，评估日志本身的成本。
5. 读取集合行数、容量、索引大小/使用证据及会话过期分布，优先平台统计与限量投影，避免为了测量执行昂贵的反复全量扫描。
6. 建立固定时钟、固定数据、固定操作的本地计数基准；真实环境验证使用隔离测试数据，避免大量写入业务家庭。

交付：按 action 和完整用户流程排序的成本表、可复现基准及前后对比模板。当前代码已有指标不代表线上已经启用，也不代表已有基线。

### B. 降低单次执行的查询和计算量（P1，先做低风险部分）

#### B1. 跨事项批量读取

- 每批候选先收集所需 ID，再批量读取当前日程片段、历史可见权、本人提醒偏好和次数状态；对 ID 去重并缓存不存在的结果。
- 将“每个事项只有一次仍单独查状态”的路径改为跨事项批次；批次大小遵循实际 SDK 限制、响应容量和执行预算，不将 20 机械扩到无限大。
- 控制记录按事项及有效区间复用；不把不同事项或不同生效边界的控制混用。保留 control.effectiveAt < boundary。
- 查询候选在事务外完成，使用现有 scope/family 版本和最终鉴权证明一致性；不为批量读取绕开写事务，也不盲目并行事务内操作。

验收：20 个各有 1 次安排的事项，其状态与偏好读取按批次增长；同数据输出、排序和权限一致。记录文档数和调用数，不能将少一次 SDK 调用直接等同少一个平台计费单位。

#### B2. 请求级执行上下文

- 显式传递 actor、scope、已验证家庭名单、实体和关联数据 Map，统一服务内部读取入口。
- 对嵌套服务共享本次请求已取得的数据；保留必要的开始/结束版本校验，移除能证明重复的中间装配和事务。
- 权限仍逐事项计算；actor、事务、成员身份和可变权限不进入模块级缓存。
- 减少重复 fingerprint、反复数组 find/includes、DTO 构建和深复制；先用计时证明热点，再用 Map/Set 或不可变对象改善，事务防串改复制不随意去掉。
- 将列表执行分为候选、鉴权、日程投影、状态覆盖、分页输出五个阶段，直接复用内部数据结构，避免服务之间通过公开 DTO 来回转换。仅围绕热点调整，不做无关大重构。

验收：普通日期列表、提醒和进度的上下文加载次数有稳定上限；双账号交错请求与撤权测试无数据泄漏。

#### B3. 数据库字段投影

- 为 summary/进度/清理引入专用存储投影与校验类型；保留鉴权、排序、版本和投影必需字段。
- 不让缺字段的记录走完整实体解析后强制类型断言；详情和写接口继续读取需要的字段。
- 清理只读取 _id、schemaVersion、expiresAt。

收益主要是传输字节、内存和解析时间；不承诺文档调用计费下降。若拆表额外增加一次读取，不为省备注字节贸然拆表。

### C. 降低首页重复执行（P1，依赖 A/B）

#### C1. 版本检查与时间失效

- 增加可选的条件读取协议；服务端在可信身份与当前成员资格验证后比较用户 scope、家庭版本、过滤条件和缓存表示。
- 未变化返回明确 unchanged 结果及服务端时间，客户端复用相同账号、环境、范围的完整结果；没有完整缓存时必须全量读取。
- 返回 nextInvalidationAt 或等价时间边界，覆盖跨天、新周期次数到时、提醒到时、日期预警变化。时间失效不依赖用户写入。
- 客户端继续按现有时效刷新，手动刷新和写入后按需重新取数；权限或范围变化立即清除相应缓存。
- 第一版复用现有 family.version，允许保守失效。只有确认频繁无关写导致显著成本时，再设计 auth/data/reminder 版本拆分并覆盖全部写路径。

验收：无变化持续前台 10 分钟只执行轻量检查；另一成员修改、退出/移除、跨天和到时仍正确刷新。缓存命中不能跳过服务端成员资格检查。

#### C2. 首页聚合读取（测量后决定是否实施）

- 若上下文重复仍显著，新增聚合 action，共享身份和家庭上下文；事项与全局提醒仍使用各自正确范围。
- 每个分区有独立完成/错误状态与续页位置；一个家庭或提醒失败不伪装成完整空结果。
- 不能简单串行包装现有三个入口；合并后应真实减少重复读取。时间预算不足时分区续读，不让一个大提醒历史拖死所有分区。
- 先兼容发布服务端，再更新客户端；旧 action 保留作为回退路径。

准入门槛：与条件读取方案相比有额外可测的总调用/GBs收益，否则不增加新契约。

### D. 候选结构与索引调整（P1/P2，收益大但兼容成本较高）

#### D1. 区分个人与家庭作用域

- 采用明确、可索引的作用域字段或规范化 familyId，兼容旧数据字段缺失；选型以实际分布、索引和查询计划为准。
- 技术回填必须有 schema/version 条件、分批检查点、并发防覆盖和可重跑机制；不改事项业务归属。
- 在回填完成前保持兼容读取；完成后个人查询只扫描个人事项，不能按 personalTaskCount=0 直接跳过全部历史，因为该计数不是完整历史证明。

#### D2. 一次性与周期历史候选分开

- 没有周期历史的普通一次性事项按作用域、生命周期、日期及稳定排序键检索。
- 有周期历史的事项不能仅按当前 schedule.kind/date 筛选；按相关日程片段寻找日期窗口候选并去重 taskId。
- 若片段增加 familyId/scope 等检索冗余字段，必须处理个人事项迁入家庭时全部相关历史片段的检索一致性。未解决前不能切换唯一读取路径。
- 评估日期上下界的保守候选字段与片段检索两个方案，选写放大更小且不漏历史者；不先建立每用户每日期的大型物化表。
- 作用域、过滤、排序联合设计索引；检查范围条件后的排序是否仍产生额外扫描，不凭索引名称判断命中。

验收：日期外一次性事项数量增长不再导致同等候选读取增长；换人、改期、一次性转周期再转回、暂停/停止与创建前一次性日期均不漏。新旧读路径离线比较完整 ID、顺序和统计，避免生产长期双读抵消成本收益。

### E. 分页与函数算法（P2，依赖 A/B）

- 当前大结果采用不可变 occurrence-run 链，后续页从头重扫块选择 top-K。改为排序块和归并游标，保存各块消费位置；沿用不可变检查点与重放语义。
- 以 N 表示次数、R 表示块数、P 表示页数。目标消除接近 P×R 的块重读；理想归并计算为 O(N log R)，实际 I/O 包含续请求恢复、权限校验和块边界开销，必须实测。
- 排序候选可用有界堆降低每候选排序成本，但页大小最多 50，只有 CPU 热点证实后再做。
- 小结果内存完成，不额外写次数块或进度树；保留已有小进度直接返回能力。
- 历史窗口沿用无数据区间跳跃，复用请求内候选；不能用任意天数截断历史，或仅依据当前日程跳过旧片段。
- 工作预算按物理读写、剩余时间和响应大小校准，保留事务余量；不能通过单纯放宽超时掩盖不收敛扫描。

验收：50/200/1000 次结果的完整分页读写曲线、同游标重放、预算中断续读、重复/遗漏、排序及统计一致性。单页变快但总页数或会话写入变多不算完成。

### F. 存储增长治理（P2；F1 可与 B 独立推进）

#### F1. 查询会话清理

- 复用 tools/cleanup-query-sessions.mjs，先修正为与 (expiresAt,_id) 一致的排序和复合游标，并投影必要字段。
- 保留过期一天宽限、已知 schema 限制、删除时条件复核和批次上限。先 dry-run 报告，实际删除另行按授权执行。
- 不假设当前 CloudBase 环境支持 MongoDB TTL；若评估平台 TTL，先核验能力与时间字段类型，不把字符串 expiresAt 直接当 TTL 日期。
- 运维执行频率根据每天新会话量制定；不新增项目禁止的定时云函数。持续执行方式确定前，清理不能标记为长期完成。
- 以会话生成速率×保留窗口×平均大小估算稳态体积，统计删除操作本身的费用。

#### F2. 冗余字段与索引

- 盘点存储中的 id/_id、identityKey、未使用 listOrder 及兼容字段，区分可推导字段和历史快照。
- codec 双读兼容后新写省略，再按收益决定是否回填旧文档；不能直接删掉解析器必需字段。
- 按查询证据检查旧个人索引、同前缀索引和排序字段；没有覆盖全部旧客户端/管理/历史路径前不删。
- 新索引建好验证后才切读；旧索引在回退窗口结束后处理。索引减少收益包括容量和写维护成本。

#### F3. 幂等回执精简（可选，最后实施）

- 按 action 统计回执平均大小与增长速度；优先识别保存完整任务/参与人快照的高频写。
- 新版契约可采用精简确认回执，但要把额外详情请求成本纳入比较；旧回执继续原结果重放。
- 不从当前任务重建历史原响应；不清理请求去重依据。若要规定重试保留期，必须先确认产品规则并解决离线未决请求，不纳入默认实施。
- 不清理历史成员、执行人快照、业务事件、提醒关闭记录或撤销后的次数版本来节省空间。

### G. 云函数运行时调优（P3，先完成算法与 I/O 优化）

- 测量初始化、SDK 创建、序列化、峰值内存与暖/冷请求的差异。
- 只有确认 SDK 可安全复用时复用无身份的客户端或不可变配置；每次请求仍独立取得可信身份。
- 在平台支持的候选内存档位上比较同工作负载的总 GBs、延迟和错误率，选择成本最优档位；不默认降内存，CPU 减少可能延长执行时间。
- 不为微小收益拆成多个云函数、不默认引入跨请求缓存服务、不增加付费实例。

## 5. 基准与回归矩阵

| 场景 | 数据与操作 | 必查结果 |
| --- | --- | --- |
| 无变化首页 | 前台连续 10 分钟、切后台再回来 | 轮询调用、数据库次数、缓存命中、到时更新 |
| 小家庭 | 1 家庭、20 事项、普通一次性与周期混合 | 首屏完整结果、上下文复用、总 GBs |
| 大家庭 | 100/500 事项、日期外一次性占多数 | 候选排除、同日期结果稳定、容量符合领域限制 |
| 多家庭 | 2/10 家庭，部分无权或加载失败 | 隔离、作用域失败显式标记、无伪完整统计 |
| 周期历史 | 每日/每周、每天 6 时刻、多年历史和长空窗 | 无漏次、控制边界、历史执行人、窗口跳跃 |
| 分页 | 50/200/1000 次可见结果 | 总读写、页数、缓存块读取、重放及中断 |
| 并发写 | 扫描期间完成/换人/退出/撤权 | 版本失效、最终权限、重启次数有界 |
| 写与重试 | 新建/编辑/记录/撤销/批量追加、响应丢失 | 原 requestId 幂等、无重复事件、回执一致 |
| 存储兼容 | 旧个人、缺字段、新旧 schema、回填竞争 | 不改归属、不漏记录、不覆盖并发写 |
| 清理 | 过期/未过期/未知 schema/扫描后被替换 | 只删除合法目标、上限与复合游标正确 |

本地基准验证结构性调用次数；平台测试验证实际计费、延迟和事务行为；双账号及真机验证协作、缓存与时间边界。三者分别报告。

## 6. 交付顺序、迁移与回退

推荐拆成可独立验收的变更：

1. A：基准、指标与成本排序。
2. B1/B2：跨事项批量读取和请求内复用。
3. B3/F1：字段投影与清理工具调整；生产清理单独执行。
4. C1：条件读取与时间失效。C2 仅在额外收益成立时实施。
5. D1/D2：作用域与日期候选，先兼容 schema/索引，再回填，再切读。
6. E：有序分页及热点计算，按大结果基准决定投入。
7. F2/F3/G：低收益或契约成本较高的项目按测量结果选做。

每项先检查 git status，保留已有修改；逻辑变化补行为测试，契约/架构/构建变化执行 npm run check。更新 database/、技术方案、SCOPE 与发布记录中对应状态。

发布采用增加兼容读取 → 建立并验证新索引 → 有界回填 → 校验 → 切换读取的顺序。旧客户端、新旧游标、旧回执均有明确策略。若游标结构无法兼容，可返回 CURSOR_EXPIRED 走既有重启，不静默误读。

保留旧路径的短期回退开关，明确移除时间；异常时回到兼容版本并保留新字段/数据，不删除集合、不恢复可能失效的权限缓存。过期会话删除不可用代码回滚恢复，因此执行前必须核验保留窗口和目标范围。

## 7. 成本验收与完成标准

成本比较采用同数据同操作序列，并将生产趋势按活跃用户、页面打开次数或业务操作数归一化，不直接比较不同流量的两天账单。

- 应用层成本代理指标 = 文档读 + 文档写 + 查询调用，同时单列事务、重试、返回行数和会话写入。该指标不替代平台计费规则。
- 实际成本 = 数据库计费调用×对应单价 + 函数调用费 + GBs 资源费 + 存储/索引及观测维护成本；以当前环境账单为准。
- 截图静态测算：数据库消耗减少 50% 约省 2352.8 点；减少 70% 约省 3293.9 点；函数消耗减少 50% 约省 106.7 点。不能叠加重叠优化的理论比例，也不据资源点推断实际现金支出。
- 每项交付包含：前后调用数/字节/会话写入、p50/p95、累计 GBs、正确性结果、真实验证范围、回退方法及剩余风险。
- 连续观察一个与原截图可比的时间窗口；达到成本目标且协作/时间/幂等无回归才标记完成。若未达标，按 action 成本排名继续定位，不以“代码更短”作为完成依据。
