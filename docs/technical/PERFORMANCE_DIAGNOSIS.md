# 页面加载性能排查

排查日期：2026-09-14。范围：当前工作区、微信开发者工具连接的真实云环境 `family-todo-d3g28fx1c314f8638`，单账号小样本。仅诊断，未修改业务代码或部署。

## 结论与测量

本次首页慢主要发生在业务接口等待阶段。首页一次刷新约 5.3 秒，最终数据更新的 `setData` 回调耗时 23ms。该回调不是完整帧率或真机绘制指标，但不支持把本次秒级等待归因于页面数据更新。

通过开发者工具内 `wx.cloud.callFunction` 计时；下表接口耗时包含传输及服务端处理，不是纯函数执行时间。

| `system.health` | 317–371ms | 3 次，不读业务数据库 |
| `family.list` | 1004–1087ms | 3 次，1 个家庭 |

实际首页并发刷新另测两次：约 6060ms、5331ms（均含用于等待回调的额外 100ms）。第二次在清空列表、显示 loading 后执行现有 refresh，今日事项请求 5213ms；约第 5223ms 提交最终数据更新，约 19.6K 字符，回调 23ms，最终恢复 ready 和 4 条事项。第一次数据未变化，差量更新没有产生 setData 调用。全部临时计时包装均在 finally 恢复。

这些不是 p95、冷启动或压力测试。没有逐个测量七个页面，也没有 iOS/Android 真机验证。

## 优化前已定位的代码原因

1. **事项候选逐条扫描，而且范围过宽。** `packages/application/src/occurrence-lists.ts:89` 以 `mode: "projection"`、`limit: 1` 扫描每个范围，未向数据库传入日期、状态条件。`packages/infra-cloudbase/src/family-store.ts:241` 的 projection 分支不筛 lifecycle；已删除事项在应用层 prepare 才丢弃。个人候选仅按 ownerUserId 查询，其中的家庭事项也是读出后过滤。每次数据库 page 读 limit+1 条但仅消费 1 条；即使最终只有几条或零条结果，也需要走完整个候选扫描。
2. **同一家庭资料重复读取。** `taskContext` 对每条家庭事项调用 `store.context`。每次 context 串行读取家庭、成员、虚拟成员、再次读取家庭版本，共至少 4 次数据库读取。周期事项还逐成员查历史执行权限；输出 DTO 时逐成员查提醒偏好。扫描结束会删除事项缓存，结果装配可能再次加载该事项和家庭上下文。权限和版本校验有必要，但当前读取复用不足。
3. **三个列表独立重复扫描。** 首页同时读取今日事项、提醒、逾期事项，各自执行完整身份/范围/候选检索。实测并发时今日请求为 5.2–5.9 秒，比逐个调用样本更慢；是否存在平台并发争用尚无服务端指标证明。
4. **页面等待最慢分支。** `miniprogram/pages/home/index.ts:44` 等待三个列表的 Promise.allSettled 后才提交事项视图；`personal-lists.ts` 还会先收齐所有分页。首页每次 onShow 刷新，onHide 清空事项，每轮成功后 30 秒再次扫描。家庭详情页串行执行 family.list → family.get → 两种状态的 virtualMember.list，最后又只展示 active，增加首屏等待；其中 progress 已单独异步显示，不阻塞家庭详情。
5. **进度有固定的额外往返。** `packages/application/src/progress.ts:113` 仅空结果直接 complete；非空结果即便已扫描完成也保存聚合和会话，返回 complete=false，下一次请求再读取聚合。实测只返回 1 个执行对象也需要两轮。

## 索引与观测边界

通过 CLI `api tcb DescribeTable` 核对 tasks、memberships、virtual_members、membership_slots、schedule_segments、schedule_controls。personal_projection、family_projection、成员、虚拟成员、用户家庭、周期片段及控制时间索引均存在；projection 索引有访问计数。不能简单归因为忘建索引，也尚未取得 explain 或单条数据库执行耗时。

函数详情为 Nodejs20.19、256MB、10 秒超时。健康接口连续约 0.3 秒而业务接口连续数秒，说明存在显著业务路径开销；没有证据支持先扩内存或归因冷启动。

CLI `fn log api --limit 30 --json` 返回 `ResourceNotFound.TopicNotExist`；SCF GetFunctionLogs 返回空，TCB GetFunctionLogDetail 亦未取得详情。因此本次不能精确拆分数据库往返、事务、函数 CPU、网络和排队各占多少毫秒。代码中的逐条扫描和重复读取是明确存在的性能放大因素，各因素比例仍需服务端分段计时确认。

## 建议处理顺序

1. 服务端优先：候选扫描改为有界批量读取，数据库提前排除已删除事项，区分个人与家庭候选；周期筛选必须保留历史片段、暂停/停止期间的合法历史，不可简单按当前日程排除。分页游标需保留未消费批次的位置。
2. 在单次请求内复用家庭基础资料和已加载事项，保留最终版本及成员权限校验；不同事项的历史执行权限单独处理，不共享可变权限结果，也不做跨请求授权缓存。
3. 非空小规模进度在预算充足时直接返回完整聚合，预算不足才使用现有续页协议。
4. 首页允许今日、提醒、逾期分区独立就绪；家庭页移除仅用于再次过滤的多余虚拟成员请求。继续保留权限失效清理与不完整统计提示。
5. 补充不含身份和内容的服务端分段耗时/读取次数，再以同一批数据复测；覆盖回收站数据增长、多家庭、周期历史和续页，随后真机验收。

## 已实施：服务端批量扫描与请求内复用

事项、提醒、次数列表共用的 `OccurrenceLists` 已将事项候选和周期片段扫描从每次 1 条改为每批最多 20 条。会话只额外保存未消费的事项/片段 ID 队列，不保存实体和权限缓存；批次尾游标与未消费队列一起续读，避免预算耗尽时跳过剩余候选。旧会话缺少队列字段时按空队列读取。原有工作预算、时间预算、排序、历史窗口和累计统计规则保留。

每次 execute 内复用已读事项及片段，事项缓存保留到返回数据生成结束；同一家庭的 active 成员基础上下文供多个事项复用。涉及离开成员和继任链的绑定仍走原校验加载路径，周期事项各自计算历史执行权限，不把历史权限写入共享上下文。请求结束即丢弃缓存，续页重新加载上下文，最终事务仍检查用户、范围版本、家庭版本和有效成员身份。

本地回归覆盖：24 条家庭事项首次请求的候选扫描从 18 次降至不超过 2 次，家庭上下文读取 1 次、无需逐条 readTask；多片段一次批量读取；事项及片段批次中断后续读无重复、无遗漏；家庭版本变化时拒绝返回旧结果。这里只证明应用层读取次数和结果正确性，不代表云数据库耗时或线上端到端加速比例。

本次未修改数据库查询筛选、索引、进度聚合协议或页面请求策略。未部署，前述真实云端耗时仍是优化前基线。
