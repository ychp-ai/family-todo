# 全量 API 性能审查与优化方案

审查日期：2026-09-15。范围：当前工作区实际注册的 43 个 action（2 个基础、19 个家庭、22 个事项/次数/提醒/进度），覆盖入口、应用用例、CloudBase 适配器、数据索引及调用复用。

本报告保留最初静态审查时的代码证据和方案，行号与实现可能已变化。后续本地改动及未完成项见 [优化落地记录](API_PERFORMANCE_IMPLEMENTATION.md)；尚未执行云端压测或部署。原有 `CLOUD_DEPLOYMENT.md`、`PERFORMANCE_DIAGNOSIS.md` 的工作区改动保留。本报告中的数量是代码路径推导，不是新增实测。旧诊断的秒级耗时属于此前版本，不能作为当前版本延迟或优化收益。

## 结论

优先减少数据库往返和重复扫描，然后降低事务竞争。主要风险不是 action 数量，而是一次列表请求内部扩展成大量逐事项、逐成员、逐次数读取，并在分页和历史窗口切换时重复这些工作。

- **P1：优先实施**——明确存在的读取放大、重复扫描和无用数据装配。
- **P2：第二阶段**——需要一致性设计、数据迁移或以实测决定的优化。
- **P3：低优先级**——目前有界、成本较小，或收益尚无证据。

所有优化保持：可信身份、当前权限校验、历史执行人、本人关闭提醒优先、持久化幂等、版本竞争保护、完整扫描后才显示最终统计。不能通过截断历史、丢弃失败家庭、减少权限检查或自动重放写入换取速度。

## 已有优化，不重复列为待办

1. `OccurrenceLists` 的事项及片段候选已每批读取 20 条，并保存未消费 ID 队列；请求内保留事项缓存。
2. 家庭当前成员基础资料已在列表请求内复用；历史执行权限已对最多 20 个 active 成员并行读取。
3. `context()` 中成员与虚拟成员并行读取；`families()` 最多 10 个家庭文档并行读取。
4. `progress.get` 首次扫描完整且预算充足时，已直接返回小规模汇总。
5. 家庭详情已复用 `family.get` 的虚拟成员；客户端已有在途读取合并与首页短期页面缓存。
6. 家庭事务已有文档缓存、80 操作上限、请求时间预算；查询已有排序游标及最终版本校验。

这些措施缓解了部分延迟，但没有消除下面的结构性开销。

## 优化清单

### 01 · P1 · 缩小日期列表的事项候选

**影响：** `task.list` 日期/逾期、`reminder.list`、`progress.get`。

**证据：** `packages/application/src/occurrence-lists.ts:101` 仅传 `mode: projection`；`packages/infra-cloudbase/src/family-store.ts:240` 的 projection 不过滤生命周期，个人查询只按 ownerUserId，家庭事项读取后才排除。已删除事项在 prepare 阶段排除。活动事项上限 500 不限制累积回收站总量，因此无结果查询仍可能昂贵。

**方案：** 先把“个人范围”和“非 deleted”作为可验证的数据库筛选条件；个人存储存在 familyId 缺失和 null 两种写法，先兼容迁移或增加统一 scopeKey，不能直接假设历史行都有 `familyId:null`。再把一次性日期候选与周期候选分流，一次性使用日期索引，周期使用保守的有效区间候选。

**索引方向：** scopeKey + lifecycle + createdOrder；一次性可进一步按 scheduleKind/date/order 设计。只是候选设计，需按真实查询计划选择，避免机械增加所有排列。当前已有 projection 索引，不能称为“缺索引导致慢”。

**验收：** 固定今日结果，加入大量删除、异日及本人创建的家庭事项后，今日候选读量不随这些无关行线性增加。不能漏 paused/stopped 的合法历史。

### 02 · P1 · 日期窗口只读取重叠日程片段

**影响：** 日期/逾期/提醒/次数列表、进度。

**证据：** `occurrence-lists.ts:119` 附近对每个事项从头读取全部 `segments(taskId)`；`family-store.ts:163` 附近片段查询仅按 taskId/listOrder。日程每次修改增加历史片段，今天查询仍处理旧片段。

**方案：** 新增有界的片段区间读取端口，取与查询时间窗相交的片段，或“窗口前最后一个片段 + 窗口内变更片段”。需证明片段连续性/边界语义后选择后者；一次性段指针、修改当刻、创建当日规则保持一致。索引与兼容回填同步设计。

**验收：** 一个事项积累数百次改期后，单日查询只处理相关片段；跨午夜、同刻改期和换人历史结果一致。

### 03 · P1 · 批量读取次数状态和控制记录

**影响：** 所有次数投影列表、进度，详情的次数解析也可复用同一能力。

**证据：** `packages/application/src/recurrence-projection.ts:48` 的 overlay 对每个有控制边界的周期候选先查询 controlBefore，再读 occurrenceState；列表逐候选 await。一天 6 个时刻、31 天最多 186 个候选，仅这两类读取在全部适用时可达 372 次，不含权限及分页重复。

**方案：** 每事项窗口一次取得窗口前最后一条控制和窗口内控制序列，按严格 `< boundary` 在内存归并；按有限批次取得候选 ID 的稀疏状态，缺行仍表示 pending/version=0。控制历史很大时分页，不能无界全量读取。事务外批量读取后，保持最终事项/范围版本栅栏。

**验收：** 读取按批次数增长；暂停/继续/停止/删除/恢复的边界结果与旧算法逐项一致；状态查询失败不得被当作缺行。

### 04 · P1 · 提醒先判断事项级开关，再展开次数

**影响：** `reminder.list`。

**证据：** `occurrence-lists.ts:137` 起先 overlay，再检查提醒资格；每个候选事务读同一事项的本人 preference 和版本，输出时又读取 reminderReceipt。个人关闭提醒也在展开后才判断。

**方案：** 当前权限验证后，每事项读取一次本人提醒偏好，不启用的事项直接跳过后续提醒投影；在能证明与状态无关的条件下，提前排除无具体时间或尚未到时的候选。回执按 occurrenceId 批量读取并在请求内复用，保留末尾版本验证。

**验收：** 全部关闭提醒时，不再为每个历史次数查控制/状态/回执；已读与收起、本人关闭、成员退出重加入、includeDismissed 均保持行为。

### 05 · P1 · 提醒与进度不要装配完整 TaskDTO

**影响：** `reminder.list`、`progress.get`。

**证据：** `occurrence-lists.ts:170` 为提醒也调用 familyTaskDTO；`progress.ts:101` 附近复用 task.list，随后只使用 occurrence。`task-context.ts:42` 起管理者 DTO 逐个读取所有活跃成员的提醒偏好。

**方案：** 抽取内部“已授权次数流”，输出 occurrence 及最小展示字段；进度直接消费次数，提醒只取标题、家庭名称、历史执行人和本人回执。保留对外契约；不要借此省略 canView 校验。

**预期：** 消除汇总/提醒中无用的 participants、note 和他人 preference 装配。20 条不同事项、20 个成员、请求者均为管理者时，完整 DTO 最多引入约 400 次 preference 文档读；实际按角色与缓存变化。

**验收：** 进度不调用 familyTaskDTO；提醒不读取他人提醒偏好；输出与旧实现一致。

### 06 · P1 · 缩小历史权限读取范围

**影响：** 所有调用 taskContext 的周期事项读取及写入。

**证据：** `task-context.ts:14` 起每个周期事项查询全部活跃成员的 historicalSubjectAccess，虽然已并行，但仍是 T×M 次点读。

**方案：** 把“校验当前 actor 可见”与“管理者完整参与人展示”分开：普通列表/历史/次数/进度只需当前 actor 的历史权利；确实展示全部参与人的详情使用批量读取。历史成员继任链另做请求内按 ID 缓存，历史执行权仍不向 successor 转授。

**验收：** 普通可见性判断随事项数而非事项×成员数增长；历史执行人可见、重加入身份不继承旧权限、管理者参与人展示不变。

### 07 · P1 · 解决 top-K 分页反复扫描

**影响：** 日期/逾期/提醒/次数列表及进度。

**证据：** `occurrence-lists.ts:156,184` 只保留 limit+1，更多候选被丢弃；保留结果消费完且 trimmed=true 后重置 scan，下一轮从头扫描，用 afterOrder 排除已发布结果。批量候选读取并没有解决此重扫。

**方案：** 优先使用按结果顺序的多路归并，为每个事项/片段保留下一候选及位置；复杂情况可按不可变查询会话分块物化“已授权候选 ID/排序键”，每次返回前重新校验范围。不能把所有实体或永久权限存进游标；会话大小和生命周期有界。

**验收：** 20/21/22/40/41/100 条以上结果，记录完整翻页累计查询量、无重复无遗漏；不随页数反复扫描整窗。范围版本变更依旧拒绝旧会话。

### 08 · P1 · 逾期与提醒跳过可证明为空的历史窗口

**影响：** `task.list(overdue)`、`reminder.list`。

**证据：** `occurrence-lists.ts:185` 每次向前移动 31 天并清空 scan，从最早事项创建日/旧 date 推导终点。多年未产生提醒的事项也可能造成大量空窗口。

**方案：** 第一阶段复用候选/片段区间元数据并跳过不相交窗口；提醒停用事项不影响提醒扫描下界。长期可建立“最早未结日期/下次提醒候选”辅助索引，但撤销完成、恢复、换人、暂停及权限变化必须同步修正；索引不可信时回退完整计算。

**验收：** 多年以前创建但目标窗口无次数的数据不会产生逐月全扫描；旧未完成记录仍能查到，不引入任意天数截断。

### 09 · P1 · 未安排和回收站继续改为批量扫描

**影响：** `task.list(unscheduled)`、`task.recycleList`。

**证据：** `collaborative-lists.ts:114` 仍调用 limit=1，适配器会取 lookahead；事项不具权限时继续逐个读取。`OccurrenceLists` 的 20 条优化没有覆盖此分支。

**方案：** 每范围维护有界批次与未消费 ID，继续按流头归并；沿用日期列表已有队列兼容做法。数据库提前排除家庭候选及非未安排周期事项，需兼容旧周期 date=null 字段。

**验收：** 100 个候选的读取轮数接近批次数，含无权候选、批次中断、续页、回收站排序及版本变化测试。

### 10 · P1 · 指定家庭的请求只加载目标家庭

**影响：** 指定家庭 task.list/recycleList、家庭事项 occurrence.list、progress.get。

**证据：** 两种列表均先 families(actor) 读取所有家庭再过滤目标；全范围的 context 仍在 for 循环里串行读取。

**方案：** 指定家庭直接读目标 family + actor slot/member 并校验；全家庭模式把独立 context 读取改为有界并发（例如 2–4 为实验起点），不是无限 Promise.all。每个失败家庭保持独立失败状态。

**验收：** 只查一个家庭时，读取量不随用户其他家庭数量增加；全范围记录峰值并发和总读取，维持原排序与失败表达。

### 11 · P2 · 简化 family.list/get 及成员列表的重复读事务

**影响：** `family.list/get`、`member.list`、`virtualMember.list`、`invitation.list/preview`。

**证据：** `family.ts:183` 起先单独 actor 事务；family.get 再做 access → context → access；family.list 两次 families()，每个家庭串行单独事务读 family/slot/member/owner。

**方案：** 首次 actor/scope/access 能共处的合并成一次有界事务；上下文提供窄投影，复用已知 family/slot/owner 信息，在末尾集中验证必要版本。family.list 的条目可按有限块验证，不能把全量事务拼到操作上限之外；成员列表维持数据库分页。

**验收：** 对 1/5/10 个家庭统计事务次数与文档读量，减少重复加载，同时覆盖读取中途退出、改名、转交和邀请撤销。现有起止校验不能直接删除。

### 12 · P2 · 普通列表返回轻量事项信息

**影响：** task.list/recycleList，以及返回 TaskDTO 的写操作。

**证据：** `familyTaskDTO` 包含 note、完整 participants、schedule 与管理者可见提醒信息。一次事项多次数结果重复携带相同 task；请求内 renderedTasks 仅节省计算，网络 JSON 仍重复。

**方案：** 优先内部批量读取 DTO 需要的偏好并做最终栅栏，减少逐事项只读事务。若端到端响应体积有明显占比，再设计摘要 DTO 或规范化 task 字典，详情再取完整内容；这需要明确契约与小程序同步改造。

**验收：** 测量响应字节数、序列化和客户端解析耗时；不以少返回必要权限字段导致错误交互。与第 05 项不同，本项可能改变公开契约。

### 13 · P1 · 消除服务分派的重复读取及无用幂等查询

**影响：** 周期 task.get/history、周期写操作、task.create/update。

**证据：** `collaborative-tasks.ts:35` 先读 existing，转给 `recurrence.ts:43` 后再次读；create/update 外层先查回执，周期服务再次查，最终事务又查。周期服务对 get/history 也先读 requestId 回执。

**方案：** 内部分派携带本次已读的 task 快照、已解析 actor 和回执查询结果；只读 action 跳过写回执查询。回执的首次查询与资源发现按流程合并，写事务中的最终回执/版本检查保留。不能跨事务复用可变事务实体或移除退出后的最小确认路径。

**验收：** 周期 get/history 没有 idempotency_receipts 查询；同一快照不重复事务外读取；丢响应、个人事项已归属家庭、并发同 requestId 测试保持通过。

### 14 · P2 · 缩短写事务，降低读写放大

**影响：** task.create/update/setAccess/restore/resume、reminder.setMine；个人一次性写操作也适用部分优化。

**证据：** `task-access.ts` 对全部活跃成员逐条读 preference；写事务末尾可装配完整 DTO，`recurrence.ts:243` 起还逐个读 nextOccurrences 的状态。个人 `saveScope` 再读一遍 scope；家庭事务缓存已避免该重复点读，个人事务尚无同类缓存。

**方案：** 将纯计算移到事务外；保留事务内需要保证一致的读取。无变化的 access 可在证明权限/名单/本人关闭状态仍正确后跳过更新；提醒.setMine 直接生成本人 preference 结果，不先生成完整 TaskDTO。个人事务引入与家庭相同语义的请求内文档缓存。若要把 DTO 移到提交后，必须先设计原回执的稳定返回语义，不能提交成功后把展示读取失败当作写失败。

**验收：** 20 个成员的最坏写路径记录读/写操作数与事务时长，低于项目操作预算；冲突重试不复用已变异对象，原回执返回不漂移。

### 15 · P2 · 将提醒状态与家庭全局版本分开

**影响：** reminder.markRead/dismiss/setMine；间接影响所有列表、family.get/list、预览和协作写入。

**证据：** 个人写统一递增 scope.revision；家庭一次性写统一保存 family.version；周期写 `recurrence.ts:228` 起还统一递增 authEpoch，包含提醒已读/收起。全列表会话绑定这些版本，小变化可使其他查询失效。不同事项写入同一 family 文档也是冲突热点。

**方案：** 分清 roster/auth 版本、事项内容/次数版本、用户提醒版本及容量计数；已读/收起只更新本人回执和相关提醒版本。长期按查询范围/分片维护内容 revision，按事项处理记录竞争；成员退出/权限变更仍提供强失效。必须同步所有写路径、游标指纹和读取校验，不能只停止增加现有 version。

**验收：** 已读操作不让无关日期/家庭列表失效；权限撤销仍立即拒绝旧会话；并发不同事项冲突率下降，容量不能超卖。是否需要进一步分片以真实冲突率决定。

### 16 · P2 · 批量追加减少固定成本和无变化写入

**影响：** task.batchAddViewers。

**证据：** `batch-viewers.ts` 起始事务逐个读子回执，单项又做回执事务及上下文读取，再进入业务事务；完成后再遍历子回执。`appendTaskViewers` 返回是否改变，但调用方忽略 false，仍写 task/family/event。

**方案：** 新项省去可合并的事务外/独立回执探测，最终事务仍检查子回执。按家庭复用基础名单与历史成员读取，成功后按已提交 family 版本更新或失效缓存；同家庭不能盲目并发。无新 viewer 且非个人归属操作时可仅保存成功回执，但“不变化是否递增 version/产生事件”的契约语义需先确定。跨家庭才考虑有限并发。

**验收：** 20 项、部分成功后断线、成功前缀重放、并发同批、权限撤销都能推进；记录每轮新增终态数及总调用数，不牺牲原 requestId/原参数重试要求。

### 17 · P2 · 退出/转交预览复用历史关系解析

**影响：** family.previewExit/previewTransfer。

**证据：** `family.ts:242` 起已按 20 条扫描，但每批重新 context(family, ids)，重复读名单与继任链；previewExit 为私密计数对多个 active 成员反复计算 rights。转交只使用 ownerBinding 判断虚拟事项，也先执行整批历史关系加载。

**方案：** 请求内缓存基础 context 与按 ID 解析的历史链；previewTransfer 使用满足计数语义的窄字段，跳过无关的 creator/owner 链解析；previewExit 每事项预先解析一次 owner/creator/必需可见集合，复用计算。以后才考虑经过一致性维护的管理反向索引。

**验收：** 500 活跃事项加大量回收站和长继任链时，查询按独立关系数增长；预览完整计数、确认 token 和家庭版本保护不变。

### 18 · P2 · 进度使用直接聚合并减少会话树往返

**影响：** progress.get。

**证据：** `progress.ts:101` 消费分页 task.list，受第 07 项重扫影响；多页更新不可变 Accumulator，目录子节点读写串行，最终树全部读回。小首屏快路径已存在，本项不重复建议该优化。

**方案：** 在第 05 项的次数流内直接聚合，不要求为了统计先按列表顺序输出 top-K；对每批按 subject 预聚合后再更新树。独立子树可有界并行，合并小节点；最后一页预算充足时直接 materialize，否则保留续页。完整最终数组仍受单次容量限制，若改为分页最终数组需另行调整契约。

**验收：** 汇总值与旧完整结果一致；多页重复重试不重复累计；记录会话读写数、历史执行人数量与最终响应大小。

### 19 · P2 · 清理过期查询会话，保留业务回执

**影响：** 所有分页/预览、进度；长期存储及查询成本。

**证据：** `family-store.ts:280` 的 saveSession 每次创建随机 ID；进度节点也通过此入口；`database/personal.md` 明确没有 TTL 清理。逻辑过期不等于物理删除。

**方案：** 为 query_sessions 增加可查询的过期索引，实施分批、可恢复的离线清理；平台自动过期能力需核对当前数据库类型和时间字段支持再选择。本项目暂不新增定时函数。不可删除未过期进度树、仍有效确认 token，也不能顺便清理幂等回执；业务回执归档需要另定保留协议。

**验收：** 所有过期会话可被清理且不影响有效续页，树共享节点按到期时间安全处理；长期容量随保留窗口而非总请求数增长。

### 20 · P2 · 统一实际工作预算与重试策略

**影响：** 全部数据库 action，尤其多页扫描和批量写。

**证据：** 家庭 store 固定 8 秒预算，扫描/装配保留 4 秒；工作单位按近似值增加，不完整代表每次成员/偏好/历史链读取。个人 store 没有同样请求截止预算；`transaction-retry.ts` 使用固定指数退避，无随机抖动。

**方案：** 建立逐请求统一 deadline，分别统计实际读写次数、候选量、CPU 和剩余时间；根据实测尾延迟为最终栅栏/保存会话预留空间。明确冲突重试采用有界 jitter，并在重试前检查 deadline。完成稳定量测之前不单纯把 4 秒保留调小或扩大 180 单位。

**验收：** 预算耗尽仍有足够时间返回可推进的游标；个人/家庭路径行为一致；同步并发时重试不集中重撞；未知提交结果仍保留待确认。

### 21 · P3 · 懒装配未使用的 store，复用安全运行时对象

**影响：** 22 个事项类 action 的入口及 identity/family SDK 初始化。

**证据：** `collaborative-tasks.ts:197` 每次先后 resolveFamilyStore 和 resolvePersonalStore，列表/进度也创建未使用的个人 store；`identity-sdk.ts` 各工厂重新 cloud.init/database；入口每请求注册全部 handler。

**方案：** legacy PersonalService 改为首次命中个人一次性分支才初始化；经 SDK 并发与实例复用验证后，缓存不带身份的数据库 client、静态 handler 定义、密钥派生结果（按密钥版本失效）。actor、store 的 deadline、事务及权限上下文仍逐请求创建。

**验收：** 分离冷/热启动、SDK 装配时间；跨账号交替与并发调用不能串身份。未证明占比前不优先重构路由，也不升级运行时或扩容。

### 22 · P1 · 补充分段观测与全 action 基线

**影响：** 全部 43 个 action。

**证据：** 现有错误适配只返回稳定错误；此前诊断没有逐条数据库/事务耗时，且没有当前优化版本的业务复测。

**方案：** 逐请求记录 action、requestId、总时长、冷/热启动、身份解析、候选/片段/状态/偏好读取数、事务次数与冲突重试、会话字节数、空续页次数、响应大小、预算退出原因。仅记录聚合指标，不写 OpenID、口令、昵称、事项内容和完整 payload。客户端另记完整分页链路与首个可见结果时间。

**验收：** 每项建议都能用读写数量和延迟分位验证；失败/超时纳入统计。只有确认 CPU/内存瓶颈后才做不同内存规格实验，不能从健康接口耗时推断冷启动是主因。

## 推荐落地顺序

1. **先量测并做低风险减读：** 22 → 05 → 13 → 04 → 09 → 10。尽量不变公开契约，先消除明确无用工作。
2. **治理随数据增长的成本：** 01 → 02 → 03 → 06 → 07 → 08 → 18。候选和投影优化必须验证历史与分页一致性；迁移索引与代码发布配套。
3. **写链路和长期运行：** 11 → 14 → 16 → 17 → 19 → 20；15 需独立一致性设计与并发验证，可先观测冲突和游标失效率。
4. **实测后再决定：** 12 的公开 DTO 改造、21 的实例复用/路由微优化及内存配置实验。

## 验证计划与通过标准

### 数据矩阵

- 个人/1 家庭/5 家庭/10 家庭；每家庭 1/5/20 个真实成员及虚拟成员。
- 事项 0/20/100/500，额外加入大量回收站事项；本人创建的其他家庭事项比例分别为低/高。
- 一次性、每日 1/6 时刻、每周；长期历史、多片段、暂停/继续/停止、已完成/跳过/撤销。
- 执行人换人、旧成员退出与继任、多次退出重加入；管理者与仅有历史执行权的成员分别查询。
- 分页边界和空续页；提醒全部关闭、全部收起及 includeDismissed；进度多页、历史执行人数量增长。
- 同家庭不同事项并发、相同事项竞争、相同 requestId 重试、调用中途失权与跨日。

### 指标

每个 action 分别记录热/冷启动下端到端 p50/p95/p99、服务端总时长、数据库/事务读写次数及耗时、事务冲突率、超时率、响应大小。列表额外记录首条可见耗时、完整结果耗时、总调用数和空续页占比；不能只测第一页。样本量不足时只报告样本和范围，不宣称稳定尾延迟。

通过标准首先是结果等价与权限/幂等不退化，其次是目标读写次数按上述方案减少，最后才评价真实延迟和费用变化。暂不承诺“提升几倍”或具体毫秒值。
